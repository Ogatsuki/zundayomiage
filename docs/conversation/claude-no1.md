  1. Claude Codeが長時間稼働できる理由

  主に以下の仕組みによります：

  1. コンテキスト管理の最適化 - 必要な情報のみを保持し、不要な履歴を自動的に圧縮
  2. ツール実行の効率性 - ファイル操作やコマンド実行が直接的で、会話のやり取りを最小限に
  3. タスク継続性 - TodoWriteツールで進捗を追跡し、中断しても再開可能
  4. 並列処理 - 複数のツールを同時実行できるため、待ち時間を削減

  トークン数自体は他モデルと大差ありませんが、これらの最適化により実質的な作業時間が延長されます。

  2. タスク分割の戦略比較

  B方式（調査→実装）の方が効果的です：

  理由：

  - コンテキストの最適化 - 調査フェーズで必要な情報のみを特定し、実装時の無駄を削減
  - エラー防止 - 事前調査により実装の手戻りを減少
  - 並列化可能 - 調査結果を基に複数タスクを並列実行可能

  トークン効率：

  実際にはB方式の方が総トークン数は少なくなることが多いです：
  - A方式：試行錯誤による無駄な処理が発生
  - B方式：的確な情報収集→効率的な実装

  プロジェクトのparallel planがまさにこの考え方を採用しています。

  4. なぜB方式が効率的か

  単純な「2倍」の話ではありません。重要なのは：

  処理トークンの削減効果

  1. 試行錯誤の削減 - A方式では処理中に何度も探索・失敗・再試行
  2. コンテキスト切り替えの削減 - 調査と実装を混在させると思考の切り替えでトークン消費
  3. 精度向上による再実行削減 - B方式は成功率が高く、やり直しが少ない

  実際の効率化要因

  - 調査結果の構造化 - Phase 1の出力が構造化されているため、Phase 2のInputは効率的
  - 並列化可能性 - 調査結果から複数タスクを分割し、別セッションで並列実行可能
  - エラー回避 - 事前調査により、実装時の大規模な手戻りを防止

  つまり、処理トークンの大幅削減がInput/Output増加を上回るということです。

  12. リソース配分の融通性

  部分的に融通が利きます！

  実際の制約モデル（推定）

  総枠: 1M トークン（仮）
  ├─ Input上限: 200k（公表値）
  ├─ 処理上限: 700-800k（推定）
  └─ Output上限: 8k/応答

  ただし：Input + 処理 + Output ≤ 総枠

  融通の実態

  - Input↔処理: ある程度トレードオフ可能
    - Input少なければ処理に多く割ける
    - Input最大なら処理は圧迫される
  - Output: 比較的独立（小さいため影響軽微）

  極端な例

  - Input 200k使用 → 処理は800kまで使えない（おそらく500k程度に制限）
  - Input 10k → 処理に900k近く使える可能性

  つまり準独立的な上限があり、総枠内での融通は利くが、各カテゴリの個別上限も存在すると考えられます。
