# マルチエージェント・アーキテクチャ仕様書

## 概要
複雑なタスクを複数の専門エージェントに分割し、並列実行と品質管理を行うシステム

## エージェント構成
### メインAI（orchestrator）
- **モデル**: Claude Opus
- **役割**: 全体統括、タスク分割、進捗管理
- **責務**:
  - ユーザー意図の理解
  - タスク依存関係の分析
  - 並列実行可能性の判断
  - 最終品質責任

### 調査エージェント（investigator）
- **モデル**: Claude Sonnet
- **役割**: 問題調査、原因分析
- **出力形式**: 構造化JSON
```json
{
  "symptoms": ["症状リスト"],
  "root_causes": [
    {"cause": "原因", "confidence": 0.9, "evidence": ["根拠"]}
  ],
  "affected_files": ["影響範囲"],
  "priority": "high/medium/low"
}
```

### 実装エージェント（worker-executor）
- **モデル**: Claude Sonnet
- **役割**: 実装作業実行
- **制約**:
  - 1タスク1ブロック原則
  - 200-800行制限
  - 自己完結性確保

### 検証エージェント（validator）c
- **モデル**: Claude Sonnet
- **役割**: 品質検証、テスト実行
- **チェック項目**:
  - 構文エラー
  - 型エラー
  - 品質基準適合性
  - MVP適性

## エラー修正フロー（詳細版）

### Phase 1: 問題調査（並列実行）
```markdown
1. メインAI起動
   - エラー内容の初期把握
   - 調査範囲の決定

2. 調査エージェント並列起動（最大3つ）
   - S1: ログ・エラーメッセージ分析
   - S2: コード静的解析（依存関係、型チェック）
   - S3: 実行時動作確認（playwright等）

3. 調査結果の統合
   - 各エージェントからJSON形式で報告受領
   - 矛盾する結果の調整
   - 原因優先度の決定
```

### Phase 2: タスク定義と分割
```markdown
4. メインAIによるタスク設計
   - 修正範囲の特定
   - タスク分割基準:
     * 機能単位（1機能=1タスク）
     * コード量（200-400行/タスク）
     * 依存関係（独立実装可能な単位）
   - タスク間依存関係マップ作成

5. タスク指示書生成
   - テンプレート: ./tasks/[3桁ID]_[タスク名].md
   - 内容:
     * 問題の背景と原因
     * 修正内容の具体的指示
     * 期待される結果
     * テストケース
```

### Phase 3: 並列実装
```markdown
6. Worker並列起動
   - 依存関係のないタスクを同時実行
   - 最大同時実行数: 4
   - 各workerに明確なスコープ割当

7. 進捗モニタリング
   - 各workerからのステータス更新
   - ブロッカー発生時の即座の対応
   - タイムアウト管理（10分/タスク）
```

### Phase 4: 品質検証
```markdown
8. 検証エージェント起動
   - 各完了タスクに1つの検証エージェント
   - 並列実行で効率化

9. 品質チェック実行
   ```bash
   # 必須3点セット
   node .agent-tools/quality-checker.js --path [project] --block [name]
   node .agent-tools/quality-checker.js --path [project]
   node .agent-tools/mega-qa.js --path [project]
   ```

10. 評価基準（5段階評価）
    - 自己完結性: 他ブロックへの依存なし（5点満点）
    - 指示適合性: タスク指示との一致度（5点満点）
    - 品質基準: lintエラー、型エラーなし（5点満点）
    - MVP適性: 過剰実装なし（5点満点）
```

### Phase 5: 修正サイクル
```markdown
11. 修正判定
    - 4点以下の項目がある場合、修正必須
    - 修正内容の具体的指示作成

12. 修正実行
    - 該当workerのみ再起動
    - 修正完了まで9-11を繰り返し
    - 最大修正回数: 3回（それ以上はエスカレーション）
```

## 新規作成フロー（詳細版）

### Phase 1: 要件分析
```markdown
1. メインAI起動
   - ユーザー要件の詳細把握
   - 不明確な点の質問生成と確認

2. アーキテクチャ決定
   - FCIS+SMAC or PVBP選択
   - 層別責務の明確化
   - 技術スタック確認
```

### Phase 2: 設計と分割
```markdown
3. 機能設計
   - 機能一覧の作成
   - UI/UXフロー定義
   - データフロー設計

4. タスク分割
   - 分割基準:
     * Core層: ビジネスロジック単位
     * State層: 状態管理単位
     * Shell層: UI コンポーネント単位
   - 各タスク200-800行目安

5. 依存関係グラフ作成
   - 実装順序の決定
   - 並列実行可能タスクの特定
   - クリティカルパスの明示
```

### Phase 3: 実装フェーズ
```markdown
6. タスク指示書作成（バッチ処理）
   - 全タスクの指示書を一括生成
   - テンプレート適用
   - タスク間整合性確認

7. Worker並列起動
   - 第1波: 依存関係なしタスク（Core層中心）
   - 第2波: 第1波完了後タスク（State層）
   - 第3波: UI層タスク（Shell層）

8. 統合テスト準備
   - 各層の結合点確認
   - E2Eテストシナリオ作成
```

### Phase 4: 品質保証
```markdown
9. 段階的検証
   - 単体レベル: 各ブロックの品質検証
   - 統合レベル: 層間連携の確認
   - システムレベル: E2E動作確認

10. 検証エージェント並列実行
    - タスクごとの個別検証
    - 統合検証の実施
    - パフォーマンス測定
```

### Phase 5: 最終調整
```markdown
11. 問題の優先度付け
    - Critical: 動作しない
    - Major: 機能不足
    - Minor: 品質問題

12. 修正サイクル
    - Criticalから順次対応
    - 影響範囲を考慮した修正
    - 回帰テストの実施
```

## 並列実行管理

### 依存関係マトリックス
```

------|--------|----------------

T004  | T001   | Group-2

## エラーハンドリング

### タイムアウト処理
- Worker実行: 10分でタイムアウト
- 検証実行: 5分でタイムアウト
- 全体: 60分でエスカレーション

### リトライ戦略
- 一時的エラー: 3回まで自動リトライ
- 永続的エラー: メインAIが判断して代替策

### エスカレーション
- 3回修正しても解決しない場合
- 依存関係でデッドロック発生時
- ユーザー介入が必要な場合

## 成功基準

### 定量指標
- 全タスク完了率: 100%
- 品質スコア平均: 4.0以上
- 修正回数: 3回以内
- 実行時間: 60分以内

### 定性指標
- ユーザー要件の充足
- コードの保守性
- アーキテクチャ準拠
- ドキュメント完備
