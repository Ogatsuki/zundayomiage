# 並列実行ガイド - ハイブリッド方式（FCIS+SMAC準拠）

## 概要
このドキュメントは、改善された並列実行プロトコル（ハイブリッド方式）の完全ガイドです。
調査・設計・実装を効率的に並列化する新しいアプローチを採用しています。

## ハイブリッド方式の特徴

### セッション1の役割（調査・設計）
- **調査フェーズ**: 問題の根本原因分析（investigator統合）
- **全体設計**: アーキテクチャ決定、契約定義
- **タスク分割**: 垂直分割優先の並列タスク設計
- **指示書生成**: 各セッション用の完結した指示書

### 並列セッション（A,B,C）の役割（実装）
- **詳細計画**: 契約内での最適実装方法決定（自律的）
- **実装**: FCIS+SMAC準拠のコード作成
- **検証**: 品質確認（validator相当）

## 実行フロー詳細

### Phase 1: セッション1での計画生成

#### 1-1. トリガー
```
ユーザー: parallel plan: [タスク内容]
例: parallel plan: voicevoxのエラー修正とUIスタイル適用
```

#### 1-2. 自動調査（Investigator統合）
```
AIの処理:
1. エラー症状と根本原因の特定
2. FCIS+SMAC層別の影響分析
   - Core層の問題点
   - State層の問題点
   - Shell層の問題点
3. 依存関係マッピング
```

#### 1-3. 全体設計
```
AIの処理:
1. 解決アプローチの決定
2. 共通インターフェース・契約定義
3. タスク間の制約事項明確化
```

#### 1-4. タスク分割と指示書生成
```
AIの出力:
- 各セッション用の独立した完結指示書
- コピペ可能な形式で明確に区切って表示
- ファイル保存:
  - ./parallel-sessions/session-a.md
  - ./parallel-sessions/session-b.md
  - ./parallel-sessions/session-c.md
```

### Phase 2: 並列セッションでの実装

#### 2-1. セッション起動
```
ユーザーの作業:
1. 新しいClaude Codeウィンドウを3つ（A,B,C）開く
2. 各ウィンドウに対応する指示書をコピペ
```

#### 2-2. 各セッションでの自律実行
```
セッションA:
1. 詳細実装計画（15分）- 契約内での最適解探索
2. 実装（45分）- FCIS+SMAC準拠コード作成
3. 検証（15分）- ビルド・型チェック・品質確認

セッションB, C:
[同様に自律的に実行]
```

## タスク分割戦略

### 垂直分割（推奨）
機能単位で全層（Core/State/Shell）を含む独立タスク：

```
良い例:
- セッションA: voicevox機能全体の修正
- セッションB: status-display機能の新規実装
- セッションC: UIスタイリング全体の適用

各セッションが機能として完結
```

### 水平分割（必要時のみ）
同一層での横断的な変更が必要な場合：

```
例外的な使用:
- セッションA: 全Core層の共通ユーティリティ
- セッションB: 全State層の状態管理統一
- セッションC: 全Shell層のReact Hooks整理

※依存関係に注意が必要
```

## 重要な変更点（v3.0）

### 旧方式との違い
| 項目 | 旧方式 | 新方式（ハイブリッド） |
|------|--------|------------------------|
| 調査 | 各セッションで個別実施 | セッション1で統合実施 |
| 設計 | 各セッションで判断 | セッション1で全体設計 |
| 契約 | 暗黙的・事後調整 | 明示的・事前定義 |
| 実装計画 | 完全に各セッション任せ | 全体設計＋詳細は自律 |
| 指示書 | 1ファイルにまとめ | セッション別独立ファイル |

### メリット
1. **効率性**: 調査の重複を排除
2. **整合性**: 契約による統一性確保
3. **自律性**: 詳細実装の創造性維持
4. **明確性**: コピペ可能な独立指示書

## 実装のベストプラクティス

### セッション1での心得
- 徹底的な調査で問題を完全理解
- 明確な契約定義で曖昧さを排除
- 垂直分割を優先してタスク設計
- 各セッションが自律的に動ける指示書作成

### 並列セッションでの心得
- 与えられた契約を厳守
- 契約内で最適な実装を追求
- 他セッションの存在を意識しない
- 完了基準を全て満たすまで作業

## トラブルシューティング

### Q: 実装中に契約の不備を発見
A: 契約の範囲内で最善の判断。重大な場合はセッション1に戻って再設計。

### Q: 他セッションとの統合で問題発生
A: 契約違反がないか確認。契約を守っていれば統合は成功するはず。

### Q: タスクが大きすぎて1セッションで完結しない
A: セッション1でより細かい垂直分割を検討。機能をサブ機能に分解。

### Q: 調査だけで時間がかかりすぎる
A: 複雑な問題は先に単独でinvestigateモード実行後、parallel planを使用。

- [ ] 契約定義は明確か
- [ ] ファイル編集の重複はないか
- [ ] 完了基準は検証可能か

### 並列実行後
- [ ] 全セッションがビルド成功か
- [ ] 型チェックが通過するか
- [ ] 統合テストが成功するか
- [ ] パフォーマンスに問題はないか

## モード使い分けマトリックス

| 状況 | 使用モード | 理由 |
|------|------------|------|
| 原因不明のエラー | investigate単独 → parallel plan | 詳細調査が必要 |
| 明確な複数タスク | parallel plan直接 | 調査フェーズ統合で効率化 |
| 単一機能の修正 | investigate → implement → validate | 並列化不要 |
| 大規模リファクタリング | parallel plan | 垂直分割で並列化 |

## まとめ

ハイブリッド方式により、調査・設計・実装の最適なバランスを実現：

1. **セッション1**: 調査と全体設計に集中
2. **契約定義**: 明確なインターフェースで統合を保証
3. **並列実装**: 各セッションが自律的に最適解を追求
4. **品質保証**: 各セッションで検証を実施

この方式により、**効率性**と**品質**を両立した並列開発が可能になります。
