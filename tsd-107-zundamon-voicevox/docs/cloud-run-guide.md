## 🏥 ヘルスチェックとは

### 基本概念

**ヘルスチェック** = コンテナが正常に動作しているかを定期的に確認する仕組み

```
コンテナ起動 → ヘルスチェック → 正常なら次の処理
             ↓
         異常なら再起動
```

### 3種類のヘルスチェック

| タイプ | 日本語名 | 目的 | 実行タイミング |
|--------|----------|------|----------------|
| **Startup Probe** | 起動プローブ | 初回起動完了の確認 | 起動時のみ |
| **Liveness Probe** | 生存性プローブ | 動作継続の確認 | 運用中常時 |
| **Readiness Probe** | 準備完了プローブ | リクエスト受付可能の確認 | 運用中常時 |

### 起動プローブ（Startup Probe）- 今回の重要ポイント！

**役割**: 「このコンテナは完全に起動したよ！」を教える

```
VOICEVOX Engine起動中...
↓
起動プローブ: GET /version (失敗)
↓
まだ起動中...
↓
起動プローブ: GET /version (成功！)
↓
「OK！Next.jsコンテナを起動してもいいよ」
```

**設定例**:
```yaml
起動プローブ:
- エンドポイント: /version
- ポート: 50021
- 初期遅延: 30秒  # 起動に時間がかかるため
- チェック間隔: 10秒
- 成功判定: HTTP 200 が1回返ればOK
```

### あって嬉しいこと ✨

1. **確実な起動順序**: 依存関係のあるコンテナが完全に準備してから次が起動
2. **エラー防止**: APIがまだ準備できていないのにアクセスすることを防ぐ
3. **自動復旧**: 異常を検知したら自動でコンテナを再起動
4. **運用安定性**: 問題の早期発見と自動対応

## 🔧 環境変数とは

### 基本概念

**環境変数** = コンテナ内のアプリケーションに設定値を渡す仕組み

```
コンテナ外部 → 環境変数 → コンテナ内アプリ
            （設定情報）
```

### なぜ環境変数を使うの？

| 従来の方法 | 環境変数の方法 |
|------------|----------------|
| 設定をコードに直書き | 設定を外部から注入 |
| 環境ごとに違うコードが必要 | 同じコードで異なる環境に対応 |
| 秘密情報がコードに残る | 秘密情報を安全に管理 |

### 実際の例

**悪い例** (コードに直書き):
```javascript
// 本番環境とテスト環境で違うコードが必要...
const apiUrl = "http://localhost:50021"; // これだと本番で動かない！
```

**良い例** (環境変数):
```javascript
// どの環境でも同じコードで動く！
const apiUrl = process.env.NEXT_PUBLIC_VOICEVOX_URL;
```

## ⚙️ 実際の設定例

### VOICEVOX Engineコンテナ

| 環境変数名 | 値 | 意味 | なぜ必要？ |
|------------|-----|------|-----------|
| `PORT` | `50021` | APIポート番号 | アプリがどのポートで起動するか指定 |
| `VOICEVOX_ENGINE_HOST` | `0.0.0.0` | バインドするホスト | 外部からのアクセスを受け付ける |
| `VOICEVOX_ENGINE_PORT` | `50021` | エンジンポート | PORTと同じ値を明示的に指定 |
| `VOICEVOX_CORS_POLICY_MODE` | `all` | CORS設定 | Next.jsからのAPIアクセスを許可 |
| `VOICEVOX_ALLOW_ORIGIN` | `*` | アクセス許可元 | すべてのオリジンからのアクセスを許可 |
| `VOICEVOX_CPU_NUM_THREADS` | `4` | CPUスレッド数 | パフォーマンス最適化 |

### Next.jsアプリコンテナ

| 環境変数名 | 値 | 意味 | なぜ必要？ |
|------------|-----|------|-----------|
| `NODE_ENV` | `production` | Node.js実行環境 | 本番環境用の最適化を有効化 |
| `NEXT_PUBLIC_VOICEVOX_URL` | `http://localhost:50021` | VOICEVOX APIのURL | マルチコンテナ内での通信先を指定 |

### 特別な環境変数の説明

#### `NEXT_PUBLIC_` プレフィックス
```javascript
// ❌ VOICEVOX_URL → ブラウザからアクセスできない
// ✅ NEXT_PUBLIC_VOICEVOX_URL → ブラウザからアクセスできる

// フロントエンド（ブラウザ）で使える
const apiUrl = process.env.NEXT_PUBLIC_VOICEVOX_URL;
```

#### マルチコンテナでの `localhost`
```yaml
# 同じPod内のコンテナ同士は localhost で通信可能
VOICEVOX Engine: ポート 50021
Next.js App: http://localhost:50021 でアクセス
```

## 🎉 メリット・デメリット

### ✅ メリット

#### ヘルスチェック
- **安定性向上**: 異常時の自動回復
- **起動順序保証**: 依存関係の確実な制御
- **監視効率**: 問題の早期発見
- **運用コスト削減**: 手動対応の削減

#### 環境変数
- **設定の柔軟性**: 環境ごとに異なる設定を注入
- **セキュリティ**: 秘密情報をコードから分離
- **再利用性**: 同じコードで複数環境に対応
- **保守性**: 設定変更時のコード修正不要

### ⚠️ デメリット・注意点

#### ヘルスチェック
- **起動時間延長**: プローブ分だけ起動が遅くなる
- **リソース消費**: 定期的なチェックでCPU・ネットワークを消費
- **設定複雑化**: 適切な値の設定が必要

#### 環境変数
- **設定ミス**: 誤った値で予期しない動作
- **可視性**: 設定がコードから見えづらい
- **デバッグ困難**: 環境変数の値を確認する手間

## 🛠️ トラブルシューティング

### よくある問題と解決法

#### 1. 起動プローブが失敗する

**症状**: `startup probe failed` エラー

**原因と解決法**:
```yaml
❌ 初期遅延が短すぎる
初期遅延: 10秒 → VOICEVOX起動に30秒かかる

✅ 適切な初期遅延を設定
初期遅延: 30秒 → 余裕を持った設定
```

#### 2. 環境変数が効かない

**症状**: APIにアクセスできない

**チェックポイント**:
```bash
# 1. 環境変数が正しく設定されているか確認
echo $NEXT_PUBLIC_VOICEVOX_URL

# 2. Next.jsの場合、NEXT_PUBLIC_ プレフィックスが必要
❌ VOICEVOX_URL=http://localhost:50021
✅ NEXT_PUBLIC_VOICEVOX_URL=http://localhost:50021

# 3. マルチコンテナではlocalhostを使用
❌ NEXT_PUBLIC_VOICEVOX_URL=http://voicevox:50021
✅ NEXT_PUBLIC_VOICEVOX_URL=http://localhost:50021
```

#### 3. コンテナ間通信ができない

**症状**: `Connection refused` エラー

**確認項目**:
```yaml
1. ポート番号の一致
   VOICEVOX: ポート 50021
   Next.js: http://localhost:50021

2. ホストの設定
   VOICEVOX_ENGINE_HOST: 0.0.0.0  # すべてのIPからのアクセスを許可

3. 起動順序
   VOICEVOX → Next.js の順序で起動
```

### デバッグコマンド

```bash
# コンテナ内で環境変数確認
kubectl exec -it [pod-name] -c [container-name] -- env

# ヘルスチェックエンドポイントを手動確認
curl http://localhost:50021/version

# ログ確認
gcloud logging read "resource.type=cloud_run_revision"
```
